DB 컬럼 딕셔너리

목적

DB table, column, type, nullable, index, FK, code set을 통일한다. API field와 DB column은 서로 역참조할 수 있어야 한다.

DB 접근 방식 결정

현재 DB 접근 방식은 MySQL 8.4 + Flyway SQL migration + Spring JDBC JdbcTemplate로 결정한다.

  • MVP 단계에서는 테이블/컬럼이 자주 조정되므로 SQL 마이그레이션과 명시적 row mapping이 변경 영향을 가장 좁게 드러낸다.
  • JSON 파일 저장소에서 MySQL repository로 순차 전환하는 중이므로, 기존 저장소 계약을 유지한 채 SQL만 교체하는 방식이 안전하다.
  • 내부관리자 조회, 백업 export, 운영 로그처럼 집계/운영 SQL이 늘어나는 영역은 실제 실행 SQL을 문서와 코드에서 바로 확인하는 편이 운영 검증에 유리하다.
  • 현재 도메인은 복잡한 객체 그래프보다 명확한 업무 테이블과 값 객체 중심이므로 ORM 영속성 컨텍스트의 이점이 크지 않다.

JPA/QueryDSL은 주문/출고/고객 간 연관 조회와 동적 검색 조건이 충분히 늘고, DB repository 전환 뒤 테이블 구조가 안정화되면 재검토한다.

일반명 사용 제한

phone, name, address, status, type, date, amount 같은 일반명은 단독 column으로 사용하지 않는다. 각 테이블의 primary key인 id와 audit column은 예외다.

Master table 적용 기준

화면 표시명, 정렬, 활성 여부가 필요하거나 운영자가 선택/필터링하는 값은 master table에 둔다. 내부 처리 흐름, 배치, 업로드, AI job처럼 시스템 로직 전이에 강하게 묶인 값은 application enum으로 둔다.
